# План внедрения сквозного шифрования (E2EE) в мессенджер

**Версия:** 1.0  
**Протоколы:** Signal Protocol (X3DH + Double Ratchet) — личные чаты, Sender Keys Protocol — групповые чаты  
**Алгоритм шифрования медиа:** AES-256-GCM

---

## 1. Обзор

Сквозное шифрование (End-to-End Encryption, E2EE) обеспечивает защиту переписки на уровне клиентских устройств. Сервер хранит и передаёт только зашифрованные данные — ни администратор сервера, ни третьи лица не могут прочитать содержимое сообщений, файлов или голосовых.

Внедрение E2EE разделено на два подэтапа:
- **Подэтап A** — E2EE для личных (1:1) чатов
- **Подэтап B** — E2EE для групповых чатов

---

## 2. Подэтап A — E2EE для личных чатов

### 2.1. Криптографический протокол

Используется **Signal Protocol** — тот же протокол, что и в Signal, WhatsApp, Google Messages:

- **X3DH (Extended Triple Diffie-Hellman)** — протокол установления сессии между двумя пользователями, даже если один из них оффлайн
- **Double Ratchet** — протокол обновления ключей при каждом сообщении, обеспечивающий forward secrecy (компрометация одного ключа не раскрывает остальные сообщения)

### 2.2. Бэкенд — хранение и раздача ключей

| Компонент | Описание |
|-----------|----------|
| Миграция БД (Flyway V6) | Создание таблиц `e2ee_identity_keys`, `e2ee_signed_pre_keys`, `e2ee_pre_keys` для хранения публичных ключей пользователей |
| REST API `/api/v1/keys/register` | Регистрация набора ключей пользователя (identity key, signed pre-key, 100 одноразовых pre-keys) |
| REST API `/api/v1/keys/bundle/{userId}` | Получение pre-key bundle другого пользователя для установления сессии |
| REST API `/api/v1/keys/count` | Проверка количества оставшихся one-time pre-keys на сервере |

Сервер выступает только как хранилище публичных ключей и транспорт зашифрованных данных. Приватные ключи никогда не покидают устройство.

### 2.3. Мобильное приложение — шифрование сообщений

| Компонент | Описание |
|-----------|----------|
| Генерация ключей | При первом входе автоматически генерируются: Identity Key Pair, Signed Pre-Key, 100 One-Time Pre-Keys. Приватные ключи сохраняются в `FlutterSecureStorage` (Keychain на iOS, Keystore на Android) |
| Установление сессии | При открытии чата с новым собеседником клиент загружает pre-key bundle и создаёт Signal-сессию |
| Шифрование текста | Каждое текстовое сообщение шифруется через Signal Protocol перед отправкой. На сервере хранится только base64-шифротекст |
| Расшифровка текста | При получении сообщения через WebSocket клиент расшифровывает его локально |
| Fallback | Если ключи собеседника недоступны, сообщение отправляется без шифрования (для обратной совместимости) |

### 2.4. Шифрование медиафайлов

| Тип | Механизм |
|-----|----------|
| Фото | Файл шифруется **AES-256-GCM** случайным ключом → зашифрованный файл загружается на сервер как `.enc` → AES-ключ шифруется через Signal-сессию и передаётся в поле `encryptedFileKey` |
| Видео | Аналогично фото: AES-256-GCM + Signal для ключа |
| Голосовые сообщения | Аналогично: записанный аудиофайл шифруется AES-256-GCM, ключ — через Signal |

На сервере все медиафайлы хранятся в зашифрованном виде (`.enc`). Расшифровка происходит только на устройстве получателя.

### 2.5. Push-уведомления

Зашифрованные сообщения не раскрывают содержимое в push-уведомлениях:
- Заголовок: **имя отправителя**
- Тело: **"Новое сообщение"** (без содержания)

### 2.6. UI-индикаторы

| Элемент | Описание |
|---------|----------|
| Иконка замка | Зелёный замок в заголовке чата — индикатор активного E2EE |
| Меню «Шифрование» | Три точки → «Шифрование» — отображает информацию о сквозном шифровании и **код безопасности** для верификации собеседника |
| Превью на главном экране | Расшифрованный текст из кэша, или «🔒 Зашифрованное сообщение» если сессия неактивна. Для медиа: «🔒 Фото», «🔒 Видео», «🔒 Голосовое сообщение» |
| Нерасшифрованные сообщения | Если расшифровка не удалась — отображается «Не удалось расшифровать» вместо шифротекста |

### 2.7. Обратная совместимость

- Старые сообщения (до внедрения E2EE) продолжают отображаться как обычно
- Поле `encrypted` в БД отличает зашифрованные сообщения от обычных

## 3. Подэтап B — E2EE для групповых чатов

### 3.1. Криптографический протокол

Используется **Sender Keys Protocol** (применяется в Signal и WhatsApp для групповых чатов):

- Каждый участник группы создаёт свой **SenderKey** — один ключ для шифрования своих сообщений всей группе
- SenderKey распределяется каждому участнику индивидуально, зашифрованный через существующую 1:1 Signal-сессию
- Это эффективнее, чем шифровать каждое сообщение отдельно для каждого участника (O(1) вместо O(N))

### 3.2. Бэкенд — распределение Sender Keys

| Компонент | Описание |
|-----------|----------|
| Миграция БД (Flyway V7) | Создание таблицы `group_sender_keys` для хранения зашифрованных SenderKeyDistributionMessage (SKDM) |
| REST API `/api/v1/groups/sender-keys/distribute` | Загрузка зашифрованных SKDM для участников группы |
| REST API `/api/v1/groups/sender-keys/pending` | Получение pending (ещё не полученных) SKDM для текущего пользователя |
| REST API `/api/v1/groups/sender-keys/consumed` | Отметка SKDM как полученных |
| REST API `DELETE /api/v1/groups/sender-keys/{groupId}` | Удаление всех Sender Keys для группы |

### 3.3. Мобильное приложение — групповое шифрование

| Компонент | Описание |
|-----------|----------|
| `GroupSenderKeyStore` | Хранилище SenderKey-записей в `FlutterSecureStorage`, с автоматической очисткой при выходе из группы |
| `GroupKeyManager` | Менеджер жизненного цикла ключей: инициализация сессии, распределение, обработка входящих, ротация |
| Инициализация | При открытии группового чата автоматически создаётся SenderKey и распределяется всем участникам |
| Шифрование | Текст/медиа шифруются через `GroupCipher` (Sender Keys), аналогично 1:1 чатам используется AES-256-GCM для файлов |
| Расшифровка | При получении — расшифровка через `GroupCipher` с использованием SenderKey отправителя |

### 3.4. Управление ключами при изменении состава группы

| Событие | Действие |
|---------|----------|
| **Добавление участника** | Все текущие участники автоматически распределяют свои SenderKey новому участнику через 1:1 Signal-сессии. WebSocket-уведомление `group_member_added` |
| **Удаление участника** | Старые SenderKeys удаляются. Все оставшиеся участники генерируют **новые** SenderKeys и перераспределяют их (ротация). Удалённый участник не сможет расшифровать новые сообщения. WebSocket-уведомление `sender_key_rotation_needed` |
| **Выход из группы** | Аналогично удалению — ротация ключей для оставшихся участников |

### 3.5. UI-индикаторы для групп

| Элемент | Описание |
|---------|----------|
| Иконка замка | Зелёный замок в заголовке группового чата |
| Меню «Шифрование» | Информация о Sender Keys Protocol, количество участников с активным E2EE |
| Индикатор набора текста | «Имя печатает...» — отображает имя конкретного участника, который набирает сообщение |
| Превью медиа | «🔒 Фото», «🔒 Видео», «🔒 Голосовое сообщение» на главном экране |
| Placeholder | До расшифровки отображается «🔒 Зашифрованное сообщение» вместо шифротекста |

## 4. Архитектура безопасности

```
┌─────────────────┐                              ┌─────────────────┐
│   Устройство A  │                              │   Устройство B  │
│                 │                              │                 │
│  Приватные ключи│                              │  Приватные ключи│
│  (Keychain /    │                              │  (Keychain /    │
│   Keystore)     │                              │   Keystore)     │
│                 │    Зашифрованные данные       │                 │
│  Signal Session ├──────────────────────────────►│  Signal Session │
│                 │◄──────────────────────────────┤                 │
└─────────────────┘                              └─────────────────┘
                          │
                          ▼
                  ┌───────────────┐
                  │    Сервер     │
                  │               │
                  │ • Публичные   │
                  │   ключи       │
                  │ • Шифротекст  │
                  │ • .enc файлы  │
                  │               │
                  │  НЕ МОЖЕТ     │
                  │  РАСШИФРОВАТЬ │
                  └───────────────┘
```

### Что хранится на сервере:
- Публичные ключи (Identity Key, Signed Pre-Key, One-Time Pre-Keys)
- Зашифрованные SenderKeyDistributionMessages (для групп)
- Зашифрованный текст сообщений (base64)
- Зашифрованные медиафайлы (.enc)
- Зашифрованные AES-ключи файлов (encryptedFileKey)

### Что НЕ покидает устройство:
- Приватные ключи (Identity Key, Signed Pre-Key, One-Time Pre-Keys)
- SenderKey-записи
- Расшифрованный контент
- AES-ключи файлов в открытом виде

## 5. Технологический стек E2EE

| Компонент | Технология |
|-----------|-----------|
| Протокол (1:1) | Signal Protocol (X3DH + Double Ratchet) |
| Протокол (группы) | Sender Keys Protocol |
| Библиотека (мобильное) | `libsignal_protocol_dart` |
| Шифрование файлов | AES-256-GCM (через `pointycastle`) |
| Хранение ключей (мобильное) | `FlutterSecureStorage` (iOS Keychain / Android Keystore) |
| Транспорт | WebSocket (STOMP) + REST API |
| БД (сервер) | PostgreSQL — таблицы `e2ee_*` и `group_sender_keys` |
| Миграции | Flyway (V6 — личные ключи, V7 — групповые ключи) |

## 7. Изменения в базе данных

### Миграция V6 — E2EE ключи (личные чаты)

```sql
-- Таблица Identity Keys
CREATE TABLE e2ee_identity_keys (
    user_id UUID PRIMARY KEY REFERENCES users(id),
    registration_id INT NOT NULL,
    identity_public_key TEXT NOT NULL,
    signed_pre_key_id INT NOT NULL,
    signed_pre_key_public TEXT NOT NULL,
    signed_pre_key_signature TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);

-- Таблица One-Time Pre-Keys
CREATE TABLE e2ee_pre_keys (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id),
    key_id INT NOT NULL,
    public_key TEXT NOT NULL,
    UNIQUE(user_id, key_id)
);

-- Поля в таблице messages
ALTER TABLE messages ADD COLUMN encrypted BOOLEAN DEFAULT false;
ALTER TABLE messages ADD COLUMN encrypted_file_key TEXT;
```

### Миграция V7 — Sender Keys (групповые чаты)

```sql
CREATE TABLE group_sender_keys (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    group_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    sender_id UUID NOT NULL REFERENCES users(id),
    recipient_id UUID NOT NULL REFERENCES users(id),
    distribution_message TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now(),
    consumed BOOLEAN DEFAULT false,
    UNIQUE(group_id, sender_id, recipient_id)
);
```

## 8. API-эндпоинты E2EE

### Личные чаты

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/v1/keys/register` | Регистрация ключей пользователя |
| GET | `/api/v1/keys/bundle/{userId}` | Получение pre-key bundle |
| GET | `/api/v1/keys/count` | Количество оставшихся pre-keys |

### Групповые чаты

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/v1/groups/sender-keys/distribute` | Распределение SenderKeys участникам |
| GET | `/api/v1/groups/sender-keys/pending` | Получение pending SenderKeys |
| POST | `/api/v1/groups/sender-keys/consumed` | Отметка SenderKeys как полученных |
| DELETE | `/api/v1/groups/sender-keys/{groupId}` | Удаление SenderKeys группы |

## 9. WebSocket-события E2EE

| Событие | Когда отправляется | Действие на клиенте |
|---------|-------------------|---------------------|
| `group_member_added` | Добавлен новый участник в группу | Распределить SenderKey новому участнику |
| `sender_key_rotation_needed` | Участник удалён или покинул группу | Сгенерировать новый SenderKey и распределить оставшимся |
